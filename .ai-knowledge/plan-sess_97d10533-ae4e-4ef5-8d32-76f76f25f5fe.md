## Diagnose (bewiesen aus CI-Log + lokaler Reproduktion)

**Root Cause:** `gh`'s eingebauter jq-Parser wertet `test("\.(test|spec)\.(ts|tsx)$")` als **"invalid escape sequence `\.`"** (im echten `jq` ist `\.` ein gültiges Regex-Escape, aber `gh` parst String-Literale strikter). Resultat: `gh pr view … --json files --jq '… test("\.…")'` schlägt mit Parse-Fehler fehl, exit 1. Das `2>/dev/null || echo "false"` verschluckt den Fehler → `HAS_TESTS="false"` → `ARTIFACTS_OK="false"` → `exit 1` ("VERDICT ready, aber kein Spec-PR mit Tests") → `ai:ready` wird nie gesetzt.

**Bewiesen:**

- CI-Log (Run 31134104366): `Claude-Verdict: 'keins'` → Guard-Skip → `verdict="ready"` → `##[error]VERDICT ready, aber kein Spec-PR mit Tests.` → exit 1
- Lokal: `gh pr view 487 --jq '… test("\.…") …'` → `failed to parse jq expression … invalid escape sequence "\."` (exit 1)
- PR #487 hat tatsächlich `frontend/e2e/header-logo.spec.ts` (Datei existiert, Pattern matcht mit `jq` direkt = `true`)
- **Lösung bestätigt:** `endswith()` ohne Regex-Backslash liefert `true`, exit 0

**Betroffen:** genau **eine** Stelle — `02-claude-spec.yml:157`. Implement/Review/Fixup nutzen keine `test("\.…")`-Patterns (geprüft). Der Spec-Workflow hat keinen Vertragstest, der das abgesichert hätte.

**Achtung — Vorgang aufklären:** Aus der Issue-#485-Timeline folgt: Du hast `ai:ready` um 00:16:45 **manuell** gesetzt; der fehlschlagende Spec-Lauf feuerte danach (00:17:06), weil du `ai:spec-ready` erneut setzt hast. Der Bug verhindert also, dass die Pipeline `ai:ready` **automatisch** nach Spec setzt — du hast korrekt beobachtet und manuell korrigiert.

## Fix (eine Datei, zwei Zeilen)

### 1. `02-claude-spec.yml` Zeile 156-157 — Pattern gh-kompatibel machen

Ersetze `test("\.(test|spec)\.(ts|tsx)$")` durch `endswith()`-Kette (keine Backslashes, gh-Parser-kompatibel, gleiche Semantik):

```bash
# VORHER (buggy — gh jq-Parser: invalid escape sequence "\.")
HAS_TESTS="$(gh pr view "$SPEC_PR" --repo "$GITHUB_REPOSITORY" --json files \
  --jq '[.files[].path | test("\.(test|spec)\.(ts|tsx)$")] | any' 2>/dev/null || echo "false")"

# NACHHER (gh-kompatibel)
HAS_TESTS="$(gh pr view "$SPEC_PR" --repo "$GITHUB_REPOSITORY" --json files \
  --jq '[.files[].path | (endswith(".test.ts") or endswith(".test.tsx") or endswith(".spec.ts") or endswith(".spec.tsx"))] | any' 2>/dev/null || echo "false")"
```

### 2. Fehler-Sichtbarkeit verbessern (Defense-in-Depth)

Das `2>/dev/null` hat den wahren Fehler 20+ Läufe lang verschleiert. Ich entferne die Unterdrückung **nicht** (die Guard-Queries brauchen sie für fail-open), aber ich ergänze an der Artefakt-Stelle eine Diagnostic-Zeile, damit bei künftigen Fehlern sofort klar wird, _welcher_ Sub-Check scheiterte:

```bash
if [ -n "$SPEC_PR" ] && [ "$SPEC_PR" != "null" ]; then
  HAS_TESTS="$(…)"
  echo "::notice::Spec-PR #$SPEC_PR: HAS_TESTS=$HAS_TESTS"
  if [ "$HAS_TESTS" = "true" ]; then ARTIFACTS_OK="true"; fi
fi
```
